# 启动与长文性能梳理（2026-09-10）

## 结论

插件存在会放大开库和长文交互负担的代码路径，已经处理其中能明确验证的重复工作。目前 Obsidian CLI 找不到运行中的实例，尚未取得真实文档库的启用/停用对照耗时，不能认定插件是开库慢的唯一原因，也不能给出实机提速百分比。

## 已处理

| 路径 | 原行为 | 当前行为 |
| --- | --- | --- |
| 元数据索引 | 任意笔记 metadata changed 都同步所有 Markdown 视图 | 仅打开的笔记变化才安排同步 |
| 文件与布局事件 | file-open、active-leaf-change、layout-change 分别重复刷新 | 16ms 内合并刷新；布局恢复期间交给 onLayoutReady；卸载取消待执行任务 |
| 编辑器装饰 | 滚动、移动光标、尺寸变化都全文扫描和诊断 | 每个视图复用当前文档分析，只生成可见行装饰；正文改变后重算 |
| 隐藏状态栏 | 仍取全文计算字数和提示 | 隐藏时停止这部分计算 |
| 工作台背景列表 | 非自定义纸张也枚举全库图片 | 显示自定义背景选项时才读取，一次渲染内只读取一次 |

保留现有配置、导出、排版与撤销语义，没有增加依赖、改版本号或发布。精简重点是减少重复执行，未为了缩短文件而拆分大型入口或删除功能。开始任务前已有大量未提交改动，本次在这些改动上继续处理。

## 其他路径的检查与边界

- 字体：启动仍等待旧字体迁移和用户字体二进制加载；导入大量字体时可能影响启动。安全迁移带有校验和回退，暂时保留。若实机确认耗时集中在这里，再处理延迟加载及导入/卸载竞争，避免只把等待移走却引入字体恢复问题。
- 系统字体：当前仅检查少量候选名称，没有全系统字体扫描。
- 批量排版、导出和设置页标签候选会遍历文件列表，但入口由用户操作触发，未发现启动时批量读取全库正文的调用。
- 阅读模式的独立 Reader 视图受功能开关控制，当前未启用；普通阅读视图的段落处理是幂等包装，减少重复视图同步也会减少它的遍历次数。
- 编辑器首次打开或正文修改后仍需要全文分析；本次缓存针对文档不变时的重复工作，并非增量解析。状态栏与工作台仍各自计算统计，打开工作台时仍有整面板重建成本。
- 字体推荐检测、主题 CSS、其他插件和 Obsidian 自身索引的实际占比，需要实机性能记录才能判断。

## 验证

- 修改前基线：62 个测试文件、378 项通过。
- 修改后完整回归：66 个测试文件、390 项通过。
- 行为测试先复现问题：1,000 个未打开笔记的索引通知原触发 1,000 次视图同步，修改后为 0；60 个同批相关事件原触发 60 次，修改后合并为 1 次。
- 同一文档的初次绘制、选区变化、滚动：全文转字符串由 3 次变为 1 次；正文修改后重新分析。
- 覆盖 YAML/代码块保护、可见正文及空白活动行、隐藏状态栏、背景切换、首次点击不重建工作台、后续刷新和卸载取消。
- 上述为宿主替身与 CodeMirror 状态的自动化测试，不是实际开库耗时测量。

## 实机复核

本次构建同步到配置指定的本地测试库。打开测试库后确认长文滚动、光标移动、写作模式、提示标记、自定义背景及工作台首次点击正常。

若要判断原文档库的开库慢是否主要来自本插件：先保持相同的打开笔记和其他插件配置，分别测试本插件启用与停用后的完整重启，各进行数次并比较稳定耗时。首次索引与系统文件缓存会影响结果。测试库同步不会自动更新其他文档库中的插件副本。
